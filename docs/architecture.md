# Архитектура WASDify

## Назначение и стек

WASDify сохраняет исходную игру и предлагает независимые точечные улучшения.
Первая версия предоставляет CLI и Tkinter GUI над одним ядром; игровые патчи
«Подземелий Кремля» включают WASD с прямым поворотом мышью, исправление
640×400 и оптимизацию горизонтального текстурирования.

Python 3.11+, стандартная библиотека, setuptools и `src`-layout. Минимум Python
повышается только по технической необходимости с отдельным согласованием.
Windows — основная проверяемая платформа; NASM — инструмент разработки
ASM-вставок, не зависимость времени выполнения. Разрядность ASM задаётся патчем.

## Границы модулей

```text
CLI (argparse) ─┐
               ├─ Service ── Catalog + explicit patch/probe registry
GUI (ttk) ─────┘      │
                     ├─ dependency resolver + edit validator + signature search
                     └─ file-set storage transaction
```

| Подсистема | Ответственность |
|---|---|
| `catalog`, `data/games.json` | Метаданные игр, версий, патчей и переводов |
| `models` | Типизированные результаты, диагностика и протокол патча |
| `signatures` | Маскированный поиск и проверка количества совпадений |
| `engine` | Зависимости, конфликты, циклы и проверка правок |
| `patches` | Явный реестр реализаций и детекторов игр |
| `service` | Определение, анализ набора, планирование и применение |
| `storage` | Чтение, SHA-256, временный файл, бэкап, замена |
| `i18n`, `presentation` | RU/EN и общее представление результатов |
| `cli`, `gui` | Ввод пользователя, вызовы сервиса, вывод результатов |

CLI не импортирует Tkinter до запуска GUI. Работа с EXE в GUI выполняется в
рабочем потоке; обмен результатами — через очередь. Tk-переменные и виджеты
доступны только основному потоку. Управление заблокировано на время операции.
Язык и бэкап не меняют байтовый план, изменение цели или выбора патчей инвалидирует его.

## Публичные контракты

`Service` предоставляет:

```python
detect(path, game_id=None) -> Detection
list_patches(game_id) -> tuple[PatchDefinition, ...]
plan(targets, selected, game_id=None) -> Plan
apply(plan, backup=True) -> ApplyResult
```

`targets` — отображение роли в путь; сейчас разрешён только один `main`.
Несколько целей отклоняются до чтения и записи. При этом патч может объявлять
дополнительные файлы, устанавливаемые относительно каталога целевого EXE.

- `Detection`: SHA-256, размер, ID игры/версии, язык, метод `hash`, `signature`,
  `manual` или `unknown`, подсказки по имени. Подсказки не подтверждают игру.
- `PatchDefinition`: ID, RU/EN, роли, зависимости, конфликты, `implemented`.
- `Patch.analyze(targets: Mapping[str, bytes]) -> PatchAnalysis`: анализирует
  неизменяемые байты, проверяет контекст и возвращает правки, блокирующие проблемы
  или `already_applied=True`. Метод не пишет файлы. Пустой результат без статуса
  уже применённого патча считается ошибкой реализации.
- `Change`: роль, **файловое** смещение, ожидаемые байты и замена. Все смещения
  относятся к исходному снимку файла. Допустимы изменения длины; пустой ожидаемый
  диапазон допускается только для добавления в конец. Правки применяются с конца.
- `Plan`: пути, определение файла с исходным SHA-256, выбор, порядок, правки,
  уже применённые патчи, диагностика; `ready` истинно при отсутствии проблем.
- `Issue`: стабильный английский код и параметры. `WasdifyError` используется
  для ошибок отдельной операции; проблемы набора накапливаются в плане.
- `ApplyResult`: `applied` или `no_changes`, SHA-256 до/после, путь бэкапа.
- `AdditionalFile`: запись `.pak`, язык варианта или `None`, роль EXE,
  относительный путь назначения и ожидаемый SHA-256. Декларации входят в `PatchDefinition.files`.
- `PlannedFile`: владельцы-патчи, источник, абсолютный путь назначения, исходный
  хэш или `None` для отсутствующего файла, конечный хэш и действие `create`, `replace`, `no_changes`.
  Список находится в `Plan.files`.
- `ApplyResult.files`: результаты дополнительных файлов (`FileResult`) с путём,
  статусом, конечным SHA-256 и бэкапом. Общий `no_changes` означает отсутствие
  изменений во всём наборе. Старый API отдельной выгрузки setup удалён.

CLI JSON — сериализация этих структур внутри `detection`, `plan`, `result`,
`games`, `patches` или `issues`. Байты передаются в hex, пути — строками,
`ready` выводится отдельно для плана. Коды завершения описаны в README.
Это начальный API 0.1; изменения контрактов должны сопровождаться документацией и тестами.

## Определение и планирование

1. Прочитать обычный файл; ссылки и не-файлы отклонить. Рассчитать SHA-256 и размер.
2. Сопоставить известные версии. Имя может отличаться от каталогового.
3. Для неизвестного хэша запустить зарегистрированные детекторы игр по сигнатурам.
   Несколько совпавших игр — ошибка; ручной выбор не переопределяет противоречащий
   хэш или детектор. Если детектора нет, ручной выбор задаёт только контекст.
4. Проверить выбранные ID, явные зависимости, конфликты и циклы. Выполнить
   топологическую сортировку; зависимости автоматически не добавлять.
5. Проанализировать каждый патч по одному исходному снимку. Зависимость задаёт
   порядок набора, но не означает, что анализ получает уже изменённые байты.
   Каждый патч должен учитывать оригинальное и уже изменённое состояние своего участка.
6. Проверить роли, диапазоны, исходные байты и пересечения правок. Любая проблема
   блокирует весь набор; частичное применение запрещено.

Маска сигнатуры — строка вида `"8B ?? 89 46 10"`; полностью неопределённые маски
отклоняются. `find_matches` возвращает абсолютные файловые смещения в заданной
области `[start, end)`. `require_matches` дополнительно проверяет точное количество.
Патч отвечает за смысл контекста, корректные области поиска, различение исходного
и применённого состояния. Общий заголовок MZ не является достаточной сигнатурой игры.

В первой игре зарегистрированы сигнатурный детектор, `wasd` и `resolution-640x400`.
Проверяются структура NE и уникальный контекст четырёх веток выбора режима.
Неизвестный хэш допускается при совпадении сигнатуры; известный хэш не отменяет
проверку. WASD дополнительно проверяет ввод, физику и релокации NE;
готовые вставки NASM входят в пакет. `render-optimization` проверяет отдельные
RU/EN-контексты цикла текстурирования и цепочки релокаций. Игровые измерения RUS
на диагностических копиях описаны в `docs/games/dungeons-of-kremlin/benchmark.md`;
ENG и цветной вывод на монитор требуют отдельной проверки.

`numeric-hud` заменяет общий метод рисования полосок двумя полями с исходными
значками и текущими числовыми значениями. Проверяются отдельные RUS/ENG-контексты,
вызовы HUD, штатный вывод текста и все затронутые цепочки релокаций. Размер EXE
и таблицы релокаций сохраняются; патч совместим с остальными тремя патчами.

`font-scaling` использует общий вывод глифов и загрузку игрового шрифта.
Во всех режимах выбирается родной FONT8; его растр и метрики масштабируются
от 320×200 по актуальным размерам поверхности. Меню, игровые сообщения
и `numeric-hud` используют одни метрики. Контекст, состояния трёх правок
и цепочки NE-релокаций проверяются до записи; новых релокаций нет.
Подробности и ограничения: `docs/games/dungeons-of-kremlin/font-scaling.md`.

`game-settings` требует явного выбора `wasd` и `resolution-640x400`.
Общий планировщик анализирует существующие патчи по исходному снимку,
собирает их результат в памяти и добавляет NE-сегменты конфигурации. Затем
распределяет окончательные непересекающиеся правки между владельцами. Это
позволяет согласовать общие таблицы релокаций без ослабления `build_result`.
Установленное состояние проверяется воспроизведением установки, а не маркером.
Игра читает INI через штатный DOS RTL; отдельные RU/EN DOS setup сохраняют INI.
Готовые байты и общие ASM-исходники входят в пакет; NASM при запуске не нужен.
[Контракты INI, анализ и ограничения](games/dungeons-of-kremlin/settings.md).

## Дополнительные файлы и транзакция набора

`game-settings` объявляет RU/EN setup с назначением `SETUP.EXE` рядом с `main`.
Язык берётся из `Detection.language`; неизвестный или неоднозначный язык блокирует
языковые ресурсы. Язык интерфейса и имя EXE на выбор не влияют. Уже применённый
патч продолжает проверять дополнительные файлы и восстанавливает их при необходимости.

ZIP с именем `WASDify.pak` содержит только дополнительные файлы. В автономной
сборке он читается исключительно рядом с `sys.executable`; в Python-пакете — через
`importlib.resources`. Каталог, сигнатуры и готовые вставки остаются ресурсами приложения.
Выбранные записи читаются без массовой распаковки и проверяются по SHA-256 деклараций.
Дубли записей, опасные пути и ссылки отклоняются. Назначения остаются внутри папки EXE;
проверяются также ссылки и reparse points во всех компонентах пути. Совпадающие
назначения с одинаковым содержимым объединяются, разные блокируют весь набор.

`apply` повторяет анализ и сравнивает правки, порядок и дополнительные файлы с планом.
Исходные хэши и отсутствие новых назначений проверяются до подготовки и перед заменой.
Все изменяемые файлы подготавливаются рядом с назначениями, записываются с `fsync`
и проверяются. Режим существующих файлов сохраняется. Для отката сохраняются
временные исходные копии независимо от настройки постоянных бэкапов.

Постоянные бэкапы включены по умолчанию и создаются эксклюзивно для всех заменяемых
файлов; неизменённые файлы не переписываются. Ошибка подготовки или обязательного
бэкапа блокирует замену. При обычной ошибке записи набор откатывается в обратном
порядке, новые файлы удаляются. Если откат не удался, сохраняются временные копии,
а диагностика сообщает оставшиеся изменённые пути, копии восстановления и бэкапы.
Не перезаписываются файлы, изменённые другим процессом во время отката.

Это не гарантия атомарности при отключении питания. Межпроцессной блокировки нет;
игра должна быть закрыта, параллельные записи исключены. Восстановление постоянных
бэкапов выполняется вручную. Операции без дополнительных файлов используют прежнюю
транзакцию одного EXE.

Локальное окружение DOSBox и рабочие копии игр для анализа находятся в `mqa/`.
Как и `originals/`, эта папка целиком исключена из Git и не входит в пакет.

## Как добавить игру или патч

1. Создать `docs/games/<game-id>/` и зафиксировать версии, SHA-256, размер,
   происхождение исследования, методы и статус анализа. Исходники и полные дампы — в `originals/`.
2. Добавить метаданные игры и патчей в JSON-ресурс с RU/EN. Указывать только
   проверенные версии; не считать язык интерфейса языком целевого EXE.
3. Для неизвестных версий при необходимости добавить контекстный детектор в
   `GAME_PROBES`. Положительный результат означает идентификацию игры, а не
   автоматическую совместимость всех её патчей.
4. Реализовать `Patch.analyze`, проверить сигнатуры, оригинальные байты и уже
   применённое состояние. Явно зарегистрировать `(game_id, patch_id)` в
   `IMPLEMENTATIONS`, затем изменить `implemented` на `true`.
5. Добавить синтетические тесты: подходящий и неподходящий контекст, отсутствие и
   неоднозначность сигнатур, повторное применение, зависимости и пересечения.
   Проверять настоящие файлы только на рабочих копиях с разрешения пользователя.
6. Обновить `patches.md`, `analysis.md` и README. Не помещать бизнес-логику в интерфейсы.

Для будущих ASM-вставок хранить собственные `.asm` рядом с реализацией патча;
документировать команду NASM, `BITS`, точки входа, регистры, сегменты, релокации,
размер и контрольную сумму результата. Готовые полезные нагрузки включать в пакет
явно через package-data; не собирать и не скачивать их при запуске приложения.

## Автономные Windows EXE

`build.ps1` создаёт изолированное окружение `build/exe/venv` и вызывает
`scripts/build_exe.py`. PyInstaller подключается через дополнительную группу
`exe`, поэтому не является зависимостью установленной оболочки.

Собирается one-file приложение `dist/WASDify.exe` с внешним `dist/WASDify.pak` с общей точкой входа
`scripts/entry_exe.py`: без аргументов открывается GUI, аргументы передаются CLI
без изменений (включая явную команду `gui`). Сборка `--windowed` использует оконную
подсистему Windows: ни загрузчик one-file, ни приложение не создают окно консоли.
Для CLI точка входа восстанавливает `stdout` и `stderr`: сохраняет унаследованные
каналы и файлы либо подключается к существующей консоли через `AttachConsole`.
Новая консоль не создаётся. Перенаправленный вывод использует UTF-8. В интерактивном
PowerShell ожидание оконного EXE и `$LASTEXITCODE` требуют конвейера (`| Out-Host`).
Сборка использует текущий `src/`, включает только ресурсы пакета и зависимости,
в том числе Tcl/Tk. Данные `originals/` и `mqa/` в неё не попадают.
Параметры PyInstaller описаны в [официальной документации](https://www.pyinstaller.org/en/stable/usage.html).

Сборщик явно передаёт `src/wasdify/data`, `locales` и ASM/include-файлы через
`--add-data` (только JSON из data/locales; `.pak` копируется рядом с EXE). Коллекторы установленного пакета не используются: в окружении
сборки может находиться старая установленная версия WASDify.

Проверка после сборки проверяет оконную подсистему в PE-заголовке, запускает CLI
из отдельного рабочего каталога, загружает
каталог и оба перевода, проверяет версию, коды ошибок и справку команды GUI.
Также применяет патч к синтетическим RU/EN EXE, проверяет автоматическую установку
setup из внешнего `.pak` и повторное применение без изменений.
После успешной проверки удаляется устаревший `dist/wasdify-cli.exe`.
Маршрутизация без аргументов и отложенный импорт Tkinter проверяются тестами.
Архитектура EXE и системная совместимость зависят от Python, которым собирается
приложение; сборка выполняется на Windows. Минимальная версия исходного пакета
остаётся Python 3.11. Временные файлы сборки и PyInstaller хранятся в `build/exe/`.

## Документация и проверка

`docs/games/<game-id>/` содержит README, версии, анализ и статус патчей.
У каждого результата анализа должны быть версия и хэш, метод, подтверждённые
факты и отдельно гипотезы. У адресов указывать систему координат: файловое смещение,
относительное смещение в модуле или сегмент:смещение в памяти.

`unittest` использует синтетические данные. Временные каталоги тестов создаются
через `tests.support.temporary_directory` в игнорируемом `build/test-temp/`
и удаляются при выходе, в том числе при исключении. Они не зависят от `TEMP`/`TMP`
и наследуют права рабочего каталога: ограничительные ACL временных каталогов
Python 3.13+ на Windows могут мешать работе и очистке в изолированном окружении.
Прерванный процесс может оставить данные только в `build/`.

GUI-тесты проверяют реальный Tk и
пропускаются только при отсутствии Tk/дисплея. CI: Windows, минимальный Python 3.11
и актуальная стабильная ветка 3.15. При выходе новой стабильной ветки обновляется
верхняя проверяемая версия, а не минимальная. Проверять установку пакета и ресурсы
вне репозитория. Реальные игровые EXE не входят в тестовые фикстуры или wheel.
