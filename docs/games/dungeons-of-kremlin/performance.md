# Почему PKR.EXE замедляется при высоком разрешении

Исследование в Ghidra 12.1.2, 19 октября 2026 года. Образец — исходный RUS
`originals/games/pkr/RUS/PKR.EXE`, 324824 байта, SHA-256
`12f78afc0eba05f76b5dc0bb99da38d7daa20585024c0ba958fe828aa3864d28`.
Хэш повторно проверен после анализа; оригинал не изменён. ENG в этом
исследовании не анализировался. Новый патч не создавался.

## Вывод

Код содержит программную растеризацию с текстурой и таблицей освещения на
каждый пиксель, дорогую подготовку каждой строки/колонки и последующее
копирование буфера в банковую видеопамять. Разрешение увеличивает реальную
работу CPU: число пикселей в 1024×768 в 12,288 раза больше, чем в 320×200.
У вертикального цикла дополнительно растёт число переходов между 64-КБ
окнами буфера с перезагрузкой ES. Эти механизмы подтверждены инструкциями;
их доли во времени кадра и фактический FPS в рамках статического анализа
не измерялись. Последующее [игровое профилирование](benchmark.md) содержит
измерения диагностических копий RUS.

## Метод и адреса

Использован штатный загрузчик `New Executable (NE)`, язык
`x86:LE:16:Protected Mode:default`. Помимо автоанализа скрипт определяет
характерные прологи методов и начало ASM-сегмента №3: часть методов вызывается
косвенно и не попала в первоначальный список функций.
Декомпиляция сверена с листингом, особенно обращения через GS/FS/ES,
переносы и адресный размер REP MOVSD. Псевдокод Ghidra теряет часть
сегментной семантики и восстанавливает некоторые аргументы ошибочно.

Адреса ниже — **NE-сегмент:относительное смещение**. Например, `3:0090`
означает сегмент таблицы №3, а не селектор DPMI. Ghidra назначила ему
`1010:0090`; это адрес базы анализа, не установленный адрес игры.

| Участок | NE-сегмент:смещение | Файловое смещение RUS |
|---|---|---|
| Горизонтальный текстурный цикл | `3:0090` | `0xAA90` |
| Вертикальный текстурный цикл | `3:0168`, прозрачная ветка `3:0197` | `0xAB68`, `0xAB97` |
| Горизонтальный растеризатор | `37:0B12` | `0x28912` |
| Вертикальный растеризатор | `37:1074` | `0x28E74` |
| Вывод области/полного буфера | `37:08DD`, `37:0A0B` | `0x286DD`, `0x2880B` |
| Копирование в видеопамять | `40:02D9` | `0x29ED9` |
| Переключение банков VESA | `40:047D` | `0x2A07D` |
| Разбиение копирования по банкам | `40:05EB` | `0x2A1EB` |
| Вывод полного кадра/прямоугольника | `40:086A`, `40:0932` | `0x2A46A`, `0x2A532` |

Начала файловых сегментов: №3 — `0xAA00`, №37 — `0x27E00`, №40 —
`0x29C00`. Импортные операнды, изменяемые загрузчиком, нельзя принимать за
готовые значения селекторов или величину шага huge-pointer в работающей игре.

## 1. Текстурирование оплачивается за каждый пиксель

В `3:0090…00AF` выполняются загрузка текселя через GS, преобразование цвета
через FS, однобайтовая запись через ES, обновление координат и ветвления.
Обычная итерация без переносов — 12 инструкций; это не заливка через REP.
Внутри этого цикла нет вызовов VESA BIOS.

| Режим | Пикселей полного кадра | Относительно 320×200 |
|---|---:|---:|
| 320×200 | 64000 | 1 |
| 640×480 | 307200 | 4,8 |
| 800×600 | 480000 | 7,5 |
| 1024×768 | 786432 | 12,288 |

Если условно заполнить весь кадр только этим циклом, при 1024×768 получится
около 9,44 млн инструкций на проход без учёта переносов, настройки строк и
остального движка. Это расчёт нагрузки, **не замер игры**: viewport, перекрытие
полигонов, стены и интерфейс изменяют фактическое число операций.

Существующий [render-optimization](render.md) убирает две инструкции загрузки
индекса в горизонтальном цикле. Он не затрагивает вертикальный цикл,
подготовку развёрток и вывод буфера. Сокращение 12 → 10 инструкций не означает
такого же сокращения времени кадра.

## 2. Вертикальные записи и 64-КБ окна

В `3:0155` AX получает ширину из `DS:[B52C]`. Цикл `3:0168` пишет байт
и выполняет `ADD DI,AX`. При переносе `3:0175…017E` сохраняет AX, вычисляет
следующий селектор и выполняет `MOV ES,AX`. Аналогичная ветка есть у
прозрачного цикла `3:0197`.

Таким образом, соседние пиксели колонки разнесены на 640/800/1024 байта.
Для шага 1024 перенос DI возникает каждые 64 строки. Это переход окна
**оперативного буфера**, а не переключение VESA-банка.

Иллюстрация для буфера с начальным offset 0: если пройти все полные колонки
один раз, включая выполняемое исходным циклом приращение после последнего
пикселя, число таких переносов составит:

| Размер | Переносов DI в вертикальном проходе |
|---|---:|
| 320×200 | 0 |
| 640×480 | 2560 |
| 800×600 | 5600 |
| 1024×768 | 12288 |

Формула: сумма `floor((x + height*width)/65536) - floor(x/65536)` по всем
`x = 0…width-1`. Реальный размер полигонов и начальный offset изменяют числа.
На каждый перенос выполняются пять дополнительных инструкций, включая
загрузку ES. Цена проверки дескриптора в защищённом режиме и плохая локальность
вертикальных записей — дополнительные кандидаты на потери; их вклад требует
профилирования. По одному листингу нельзя объявлять их главным узким местом.

## 3. Деления на каждую развёртку

Горизонтальный растеризатор `37:0B12` перебирает Y, выбирает таблицу освещения,
вычисляет шаги текстуры и вызывает `3:0000` по `37:101A`.
На обрабатываемой строке есть `IDIV BX` по `37:0F4B` для индекса освещения и,
при непустом видимом диапазоне, два 32-битных IDIV по `37:0FBB` и `37:0FCD`
для шагов U/V. Помимо этого есть расчёты рёбер при смене участка полигона.

Вертикальный растеризатор `37:1074` перебирает X и вызывает `3:00D2`
по `37:153C`. Деление для освещения — `37:1495`, для шага текстуры —
`37:1502`. Это работа на строку/колонку каждого полигона; она растёт
с линейными размерами изображения и числом видимых развёрток.
Делений внутри собственно пиксельных ASM-циклов нет.

## 4. Готовый кадр ещё нужно скопировать

Создание поверхности `37:01D8` выделяет отдельный буфер `width*height`;
`37:0000` строит таблицу указателей строк. Текстурные циклы пишут в этот буфер.

Есть два пути вывода: `37:0A0B → 40:086A` копирует полный кадр;
`37:08DD → 40:0932` копирует заданную область и дополнительные прямоугольники.
Оба заканчиваются отдельным вызовом `40:051D` для переключения отображаемой
страницы, если включён соответствующий режим. Какая ветка доминирует в сцене,
статическим анализом не измерено.

Полный вывод режется на блоки с числом строк `floor(64000/pitch)`.
`40:05EB` проверяет 64-КБ границы видеопамяти, `40:0325` обрабатывает
границу исходного huge-pointer, `40:02D9` копирует через REP MOVSD
с хвостом REP MOVSB. Копирование **последовательное**, не через BIOS на пиксель.
Для полных кадров нужно передать минимум 307200/480000/786432 байта
соответственно, дополнительно к растеризации в RAM.

При смене банка `40:047D` делает два `INT 10h, AX=4F05h`: с BX=0 и BX=1,
устанавливая оба окна. Код запоминает банк в `DS:[C202]` и не вызывает BIOS
повторно при совпадении. Это накладные расходы на границу банка, а не на
каждый пиксель. Прямой пиксельный VESA-метод `40:0588` существует, но
исследованные текстурные ASM-циклы его не вызывают.

Ожидание retrace найдено в `35:0329` (порт 3DAh); в исследованных путях
копирования кадра прямого вызова этой функции нет. Её найденные прямые
вызовы относятся к записи палитры. Этого недостаточно, чтобы объяснять
замедление каждого кадра ожиданием вертикальной синхронизации.

## Что ещё требуется измерить

Измерений времени функций, FPS и CPU cycles в этой работе нет. Локальный
`mqa/dosbox/dosbox-staging.conf` содержит только монтирование и autoexec;
действующий лимит CPU из него определить нельзя. Указанные в прежнем
исследовании 60000 — сведения о значении по умолчанию, не замер текущего запуска.

Для определения главного узкого места нужны одинаковая сцена и маршрут,
фиксированные настройки CPU, размеры viewport и завершённые игровые кадры.
Отдельно измерять горизонтальный/вертикальный растеризаторы, копирование,
число переключений банков и прочую игровую логику; затем повторить при
разных лимитах эмулируемого CPU. FPS окна эмулятора не заменяет FPS игры.

Приоритет исследования оптимизаций: оба текстурных цикла; устранение
повторных вычислений освещения/шагов; сокращение загрузок сегментов; затем
стоимость копирования и BIOS-вызовов. Изменение способа адресации буфера
потребует отдельной проверки DPMI, релокаций и визуальной эквивалентности.
Без профиля нельзя обещать устранение тормозов одной локальной правкой.

```powershell
./scripts/analyze_pkr_ghidra.ps1 `
  -GhidraHome 'C:/path/to/ghidra_12.1.2_PUBLIC' `
  -JavaHome 'C:/path/to/jdk-21'
```

Скрипт создаёт отдельный headless-проект `PKR-performance`, использует
`scripts/GhidraPkrPerformance.java` и сохраняет проект, полный листинг и
декомпиляцию только в игнорируемый `originals/source/pkr-ghidra/`.
Существующий GUI-проект Ghidra и его настройки не меняются. Полные дампы
не являются публикуемыми артефактами или тестовыми фикстурами.
